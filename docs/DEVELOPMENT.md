# 开发与提交须知

本文只写**会在提交/推送时被机械检查**的约定。历史决策叙事见 `ops/skills/*/CHANGELOG.md`，架构说明见 `docs/ARCHITECTURE.md`。

## 一、常用命令

| 命令 | 作用 |
|---|---|
| `npm run check` | 类型检查（`tsc --noEmit`） |
| `npm run build` | 构建到 `dist/`（`dist/` 不入库，干净 clone 需先构建） |
| `npm test` | 单元测试 |
| `npm run audit` | 发布卫生审计（与 CI 第 8 步同一脚本） |
| `npm run hooks:install` | 启用版本化钩子 `.githooks/` |

## 二、pre-push 门禁

仓库采用**版本化钩子目录**（`core.hooksPath=.githooks`），钩子内容随代码一起 review，换机/重装后重新执行一次 `npm run hooks:install` 即可恢复。

行为约定：

- 推送前本地复跑 `ops/publish-audit.sh`，与 CI 同源，判据不漂移；
- **对环境影响 fail-open**：缺 `zsh` / 缺 `npm` / 构建失败时只告警、不阻断推送；
- **对审计结论 fail-closed**：审计返回非零即阻断推送；
- 确需跳过：`git push --no-verify`（CI 仍会拦截，跳过只影响本地反馈速度）。

`dist/` 未入库，钩子在缺失时会先 `npm run build` 以复现 CI 顺序——这也是本地不复现「dist 不存在」误报的原因。

## 三、发布卫生审计检查什么

`ops/publish-audit.sh` 覆盖：明文凭据、个人/工作敏感信息、记忆数据文件、git 索引中的软链、**产品品牌残留**、`dist/` 存在性、npm 打包清单洁净度。

其中**品牌残留检查的扫描面**包括 `dist/`、`src/`、`ops/`、`docs/`、`README.md`、`package.json`——注意 `ops/skills/**` 会随 npm 包发布，因此技能文档（含 CHANGELOG）也在检查范围内。

### 因此，写文档时的硬约定

- 描述历史工具名、历史任务 ID、旧产品版本时，**一律用抽象表述**（如「旧产品名」「任务 ID 前缀沿用历史命名」），**不要写字面量**；
- 需要保留取证事实时，用可核验但中性化的写法（日期 + 行为 + 结论），不复制原始标识符；
- 提交这类文档后，至少等 CI 第 8 步出结论再视为完成。

### 判据冲突时怎么办

审计命中一条**正当文档引用**时，正确做法是**改写文档**，不是给审计加白名单。给品牌门禁开例外，会把真防线变成噪声——历史上这条规则就是从三次真实事故固化来的。

## 四、提交纪律

- 技能/文档改动**当场提交**，避免"改完不提交、一周后补提交"——首次进入 CI 的内容往往已经定型，问题会延后暴露；
- 涉及 `ops/` 下文档的改动，推送前先跑一次 `npm run audit`；
- 一次提交只做一件事，便于回滚与定位。
