## 本版主题
没有新增检索能力。做完两件事：把「状态页」这个假设验证到底并按证据停用它；
修掉一个沉了一个多月的坑——**公开基准自 2026-09-11 起就跑不动了**。

## 状态页：先补完机制，再按证据停用
- **增量演化**：把上一期 active 状态页清单喂给模型，对「`supports` 里没有上期生成之后新记忆」
  的重写做机械拦截（回落沿用、不写库）。不加拦截，滚动窗口会让同一批主题每期被重写一遍。
  判据用确定性信号而非模型自述——实测它会在同一份输出里同时给出 `reuse` 和重写。
- **`supersededBy` 双向指针**：此前只写 `status/supersededAt`，演化链指向不明（库内 3 条指针全 null）。
- **`_resolve_ref` 唯一前缀解析**：模型会把 36 位 id 抄成 8 位前缀，原全等比较判它「编造 id」并丢弃
  ⇒ 演化静默失效。现支持全 id 与唯一前缀（有歧义则拒），噪声先清洗。
- **`--backfill-superseded-by`**：存量自愈，给早期缺指针的旧页补 `supersededBy`（实测回填 2 条）。
- **结论先行判据改结构性判定**：词表穷举对中文变体天然不足（依次漏掉「已解决/已发布/已排程/已成功发布」），
  改为「状态前缀起头 / 前 24 字含状态词 / 前 12 字含状态动词」三选一。
- 🔴 **然后停用它**：A/B 实测（副本库把 10 条状态页全标 superseded，跑同一套 41 题 golden）——
  core R@1 28/28、R@8 38/38、retrieval R@1 31/31、R@8 39/39、MRR 0.827 vs 0.828，**逐项相同**；
  13 条状态页 `recallCount` 仅 1 条非空（那次还是验收测试本身）＝从未被真实使用。
  ⇒ 周频生成撤除、目录注入默认关闭（`LEAFMEM_STATUS_PAGE_MAX` 默认 `0`，设 `12` 可恢复），
  数据保留为静态。README §3.7 改为「v0.3.24 引入、当前默认关闭」并写明重新启用条件。

## 基准可跑性修复 + 重测
- `remember` 自 2026-09-11 起有单条 6,000 字上限，而 LongMemEval 数据里有 15,058 字会话
  ⇒ 原「1 session = 1 条记录」的跑法直接抛 `memory content too long`，**README 挂着的 98.4%
  从那时起就无法复现**。现按上限切块入库（优先换行、其次句号，metadata 标 `part/partOf`）。
- 2026-10-22 重测（硅基流动免费额度，$0）：LongMemEval 500q 内置 89.0 / 93.4 / 0.825、
  默认配置 96.8 / 98.2 / 0.921；LoCoMo 1986q 内置 84.2 / 92.0 / 0.734。
  LME 与 08-11 旧值**不可直接比较**（切块后记录粒度变细，方法变了）；LoCoMo 方法未变、
  与旧值 84.1 / 92.0 / 0.733 **逐项持平**——这是「本日检索打分改动无退化」的证据。

```bash
node dist/bin/leafmem-mcp.js        # MCP stdio 服务
node dist/bin/leafmem-agent.js --help
```
